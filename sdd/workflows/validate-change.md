# Validate change

Use to assess a change's actual acceptance evidence. Read the [process](../process.md), [metadata](../metadata.md), current artifacts and applicable Standards. A validation-only request authorizes relevant diagnostics and evidence recording, not implementation fixes. A request solely for status remains read-only.

## Procedure

1. Locate the unique active/archive dossier. Check current planning approvals and compare requirements, design, tasks, implementation and living specifications. Report premature validation or stale planning as a gap, not implicit approval to bypass a gate.
2. Resolve the reviewed impact against effective current contracts and historical origins. Review every local scenario and preserved/extended regression obligation, including success, error and boundary behavior, against current code and living documentation even if all tasks are checked. Trace every requirement to the Design validation plan and its required checks. Assess coverage of relevant acceptance scenarios under the resolved [Testing Standard](../../standards/core/testing.md), including meaningful errors and boundaries; report gaps even when a linked check passes. Execute the relevant project tests, agent evals and Harness validators, including security, operations, rollout and rollback obligations selected by the resolved Standards. Exercise affected documented commands or UI steps and compare observed and expected outcomes under the [Documentation Standard](../../standards/core/documentation.md). Review affected language variants for equivalent instructions and results. Use observed commands/actions and results; never infer a pass from a planned test name.
3. Record results in Tasks `validation` using the [evidence contract](../metadata.md#validation-evidence). Reuse a functional check and its evidence for documented usage when they verify the same behavior; no separate documentation report is needed. For v3, capture matching `--input-digest` values before/after each actual check and its observed environment/context. Record one assessment for each local and retained regression obligation, linking the planned checks and explaining observed behavior. Only approved exclusions may use not-applicable. Bind the results to the current Tasks plan digest; record each check's actual tested revision or run and durable evidence. Use a stable repository-relative evidence path outside the movable dossier, or an observed HTTPS run/report URL. Keep a concise human-readable Validation evidence section.
4. Record missing, partial, contradictory and unrequested behavior as stable findings, with source, evidence and corrective task/check references. Reuse the same open finding on repeated review. Validation-only records it without fixing code. With existing implementation authority, correct within approved tasks and record resolution with current evidence; new task content reopens Tasks and broader changes reopen the earliest gate. Rerun affected checks after code changes even if the plan digest is unchanged. Missing credentials, environment or external access produce `unverified` and an explanation. Record actual failures as `fail`; do not mark pending tasks completed simply to satisfy delivery checks.
5. Run the SDD validator with `--change <change-id> --phase delivery` to assess completion and evidence readiness before archive preparation. Report its `pass`, `fail` or `unable-to-verify` result with actual gaps. Local schema/evidence consistency cannot prove semantic test adequacy, human identity, remote CI or merge.
6. Review branch naming, commit messages, work tracking and any proposed squash subject against the resolved Git Standard. Prepare a PR summary with approved scope, changes, actual checks and known limitations. Keep remote integration/check observations distinct from repository validation. Prepare text without publishing it unless publication is authorized.

## Exit

Return requirement coverage, executed checks, failures, unknowns and evidence links. When fixes were not authorized, describe them and stop; do not modify product code. A passing local result permits preparation of documentary closure when requested, not a claim of completed delivery. If that preparation is authorized, read [Archive change](archive-change.md); otherwise state the next permitted action.

A request to submit a completed implementation for PR review includes its routine documentary archive preparation. Follow Archive change before publishing the delivery PR or marking an existing draft ready. An explicitly limited request for a planning/draft PR or validation report may retain an active dossier; state the remaining closure work without presenting it as ready for delivery.

## PR handoff check

Do not equate an ordinary delivery pass with prepared archival: that phase is also used to authorize the move. For submission of completed work, follow Archive change and require `--change <id> --phase delivery --require-archive` after moving the dossier and checking its links. Report both archive path and closure. Planning/incomplete reviews remain draft PRs; a draft becoming ready reruns the CI archive guard. Requests limited to validation still report archival pending instead of implying PR readiness.

## Execution adapters

For projects adopting explicit execution, follow [project validation](../../docs/guides/project-validation.md). Use a full configured run with an approved automated check/context to obtain a result fragment; inspect it before copying current evidence into Tasks. Manual checks remain actual reviewed procedures. Keep failed attempts and report prerequisite failures as unverified. Assess assertions and retained behavior even when all configured suites pass. Follow [supervised Skill evaluations](../../docs/guides/skill-evaluations.md) for approved agent checks; deterministic helper tests never substitute for observed supervised behavior.
